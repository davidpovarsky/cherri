## Actual failures and production changes

### Documented migration command

The public migration companion previously ignored Boolean flags placed after the
input filename. Actual `--check` and `--write` calls before and after the file
now follow the same parser and production migration pipeline. The original
failed commands and corrected seven-event replay remain in the archive. An
initial test used unsupported `-oPATH` syntax; that assertion was corrected to
the help-documented `-o=VALUE` spelling without changing public CLI syntax.

### Original-byte capabilities validation

The old shell selector could accept malformed JSON or confuse nested/duplicate
fields with the required top-level capability identity. The new bounded POSIX
parser validates complete grammar, original UTF-8 bytes, number syntax, escapes,
surrogate pairs, decoded duplicate keys and the required scalar types. Raw NUL,
multiple documents, missing separators and non-finite/non-JSON numbers reject.
The parser stops at its input limit rather than retaining oversized input.

Protocol, catalog, schema, codec and macro identity must match the selected
component contract. Synthetic invalid responses are negative controls only:
execution of the supplied response is observed before the precise rejection is
accepted. Healthy compilation, migration and native comparisons use real tools.
The additive Linux workflow is configured to execute ten byte-level controls with
BusyBox in an inspected immutable Alpine image, with networking disabled during
the test. That job is explicitly parser-only and cannot credit formal rows.

### Both installed roles and exact source

A successful installation contains the actual compiler and `cherri-migrate`,
plus a source receipt and byte digest for each: six files in total. The companion
reports its own Go build metadata and can inspect another file's real build
identity while hashing the same open file. Main-package role, clean immutable
VCS source and target platform are checked; a forwarding shell wrapper cannot
borrow an installed binary's identity.

Compiler receipts and checksums are now verified before compiler execution.
The migration path follows the same order. An outdated but capability-compatible
binary, a wrong role, a missing companion, mismatched platform metadata and a
changed file cannot pass through reconciled external receipts alone. The final
ownership control builds a real second clean commit with the exact same Git tree
and identical semantic capabilities, then proves its different embedded source
is rejected. This avoids treating unrelated schema evolution as source-identity
proof.

Runtime packaging snapshots the actual input bytes, verifies both embedded
roles/source/platforms and emits both tools plus all four receipts. Archive
creation and verification disable Git replacement objects for commit, tree and
blob reads. The original replacement counterexamples are retained. Documentation
must be an exact clean Git checkout at its immutable pin; preserving public
fingerprint files does not authorize changed documentation bytes.

### Handled update rollback and lock ownership

The installer stages both real source-built tools and documentation before
activation. Each actual on-disk move determines rollback, including interruption
immediately after a move but before a shell state variable can change. Failed
checksums and handled signals preserve the previous six files and exact docs.
An explicit missing or wrong-role `CHERRI_MIGRATE_BIN` override is validated
before the update is committed, so readiness matches the effective selected
companion. Successful update and subsequent public migration are executed.

A signal immediately after successful lock-directory creation previously left a
stale lock because the shell had not yet recorded ownership. Acquisition now
defers the signal until mkdir's outcome establishes ownership, then cleans up
only its own lock. A pre-existing owner remains untouched. Both documentation
and source-build paths reject assume-unchanged/skip-worktree index flags without
modifying caller flags or bytes, preventing concealed edits from being stamped
as an exact clean pin.

This is evidence for handled command/signal failure rollback. It makes no claim
about simultaneous readers or sudden power loss.

## Actual consumers and explicit fixture scope

Each extracted scenario builds current production tools from a clean normal Git
clone, generates actual reference documentation, commits an owned disposable
component tuple, creates and verifies the real ZIP, extracts it, and invokes the
shipped installer and public commands. The repository's published compatibility
manifest remains byte-identical. The currently published R3 tuple is deliberately
not reinterpreted as a new R4 release.

The old shipped self-test used a fake prebuilt marker in a repository lacking a
Go module. Its actual failure is retained. It now accepts real same-source tool
bytes and uses an explicitly controlled download transport for ten installer
controls. Minimal owned docs in those transport controls are not published docs.
The independent RP45 atomic scenario still performs a real source build after
source/docs branch advancement, so source-pin obligations were not removed by
the consumer adaptation.

The shipped compatibility isolation consumer also runs with an actual same-source
pair, generated disposable docs and controlled offline execution. Nine named
selection/consumer events passed at `877c8ebe2e6537f80a9244db2a9c54d6a3e008df` in
385.109 seconds. The preceding runtime replay passed all ten controlled consumer
scenarios but failed one path-spelling assertion. That original failure remains:
Windows and MSYS forms are now compared with the existing actual file-identity
helper while requiring the unique source/role verification marker.

The real-release script is adapted to build both roles from the exact source and
verify both receipts. The OpenMinis runtime package pipeline builds and packages
both roles for each target. These changes require a fresh coherent final tuple
and actual final consumer replay; this local checkpoint does not assert that
those published consumers have passed.

## Strict independent acceptance

The new producer selects 14 exact root events for RP42, 39 for RP44 and 41 for
RP45. Every selected child must run and pass while its selected ancestors remain
active. Parent/package success cannot replace a missing child. Each of the two
tier records retains the complete independently executed scenario.

The intake binds the exact immutable implementation commit, 64 reviewed Git
source blobs, actual command, clean source before/after, bounded process interval,
original JSON event bytes and stderr hashes. It rejects missing/duplicate/extra
selection events, malformed/invalid UTF-8 output, unexecuted or reordered children,
source/byte/process corruptions, linked-ID rebinding and attempts to turn local
component results into final closure. The original first inventory replay found
our new `packaging` tier label differed from the existing canonical
`skill-package`; only the new producer label was corrected.

The dedicated workflow is registered by one exact probe-branch push. Expensive
scenario and BusyBox jobs run only after explicit dispatch. It retains all
original process output and artifacts even on failure and stops only owned
process descendants on timeout. No required project CI gate is bypassed.
